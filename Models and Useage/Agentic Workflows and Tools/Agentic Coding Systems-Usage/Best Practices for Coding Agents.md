# Using Agents.md with AI Coding Agents: Best Practices Across Platforms

## Introduction

Modern AI coding assistants (or _agentic coding systems_) can autonomously plan and execute multi-step coding tasks. Examples include **OpenAI Codex (CLI agent)**, **Anthropic’s Claude Code**, **GitHub Copilot’s “Agent Mode” in VS Code**, and **JetBrains’ Junie**. A key component in many of these systems is an _instruction file_ (often named `AGENTS.md` or similar) that serves as a guide for the AI agent. This file acts like a README for the AI – it provides project-specific context such as coding standards, testing commands, and organizational conventions that the agent should follow.

In this report, we compare how different agentic platforms use such instruction files and how to decide what details to put into **Agents.md** (or its equivalent) versus in the live prompt given to the AI. We also address how this decision varies across platforms and discuss strategies for iterative refinement in an AI-assisted coding project. Key considerations include:

- Division of _“Task Management”_ or coordinator instructions between Agents.md and prompts vs. relying on the agent’s built-in capabilities.
    
- Specification of coding standards, diligence checks, and test requirements in Agents.md vs. prompts vs. built-in platform behavior.
    
- Handling documentation-generation tasks – whether to specify output structure and detail upfront or to iterate after initial results.
    
- Iteration and refinement strategies as a project progresses with AI assistance.
    

All readers are assumed to have a software development background. The guidance aims to help engineering leads and developers make effective use of AI coding agents by tailoring instruction scope appropriately for each tool.

## Role of Agents.md (and Equivalents) in Different Platforms

**Agents.md** is a concept introduced with early coding agents (notably OpenAI’s Codex) to persistently inform the AI about project context and conventions. The Agents.md (or similarly named file) is typically placed in the project repository and automatically read by the AI agent. It often contains guidelines on: how to navigate the codebase, which commands to use for building/testing, coding style rules, and other project standards. By separating these instructions from the immediate prompt, you avoid repeating them every time and ensure the agent consistently remembers project-specific requirements.

However, not all platforms use _literally_ a file named Agents.md. The idea manifests in different ways:

- **OpenAI Codex CLI (Codex Agent)** – _Agents.md file support:_ The Codex CLI agent explicitly looks for `AGENTS.md` files in the repository or environment. These files act as a way for developers to give the agent additional instructions or tips for working in that codebase. The agent will obey any instructions in an Agents.md that pertain to files it is modifying. Typical contents include coding conventions, project structure notes, and how to run tests. Notably, the scope of an Agents.md is the directory subtree it’s placed in; nested Agents.md files override more general ones, and direct user prompts override Agents.md instructions if there’s a conflict. In practice, you’d put a global Agents.md in the repo root (and optional more specialized ones in subfolders) to guide Codex.
    
- **Anthropic Claude Code** – _Claude.md or Agents.md:_ Claude Code, a closed-source CLI coding assistant by Anthropic, uses a similar mechanism. It can load project-specific instructions from a file (commonly referred to as **Claude.md** in documentation). In essence, when starting a Claude Code session in a project, it will look for an instruction file (Claude’s docs sometimes call it `Claude.md`) containing guidelines, just as Codex looks for Agents.md. This file serves the same purpose – defining test instructions, core files or entry points, code style and best practices, etc., that the agent should remember. By providing such a file, you give Claude important context without packing it all into each prompt. (If no file is present, the agent just relies on general knowledge and the conversation, but best practice is to include one.)
    
- **GitHub Copilot Agent Mode (VS Code)** – _Repo Custom Instructions:_ Copilot’s agent mode doesn’t use an `Agents.md` by default, but it has an equivalent feature. GitHub provides **repository-level custom instructions** via a file named [`.github/copilot-instructions.md`](https://docs.github.com/en/copilot/customizing-copilot/adding-repository-custom-instructions-for-github-copilot) that you can add to your repo. This file’s contents (written in natural language Markdown) are automatically appended to all Copilot Chat prompts for that repository. The intent is similar to Agents.md: you include short, focused statements about the project for Copilot to always consider. For example, you might note “We use Bazel for Java dependencies, not Maven” or “Always conform to the coding styles defined in `STYLEGUIDE.md` for this repo”. Copilot will then take these into account in its responses. Aside from this, Copilot agent mode also allows ad-hoc context files – the interface lets you attach files as context (via an “Add Files” button or `#file` references in the prompt). This means if you have a detailed specification or design document (say `specifications.md`), you can manually include it in the context for a given query to guide the agent. Additionally, Copilot has **global user instructions** (similar to ChatGPT’s custom instructions) for general preferences, and it leverages the codebase itself (it builds a summarized view of the workspace to supply the model). In summary, Copilot’s approach is more dynamic: it doesn’t assume a static Agents.md by default, but it provides mechanisms to feed it persistent project instructions when needed (through the `.copilot-instructions.md` file or by adding context on the fly).
    
- **JetBrains Junie (IntelliJ/PyCharm AI Agent)** – _IDE-Integrated Context:_ Junie is deeply integrated with JetBrains IDEs, and while it doesn’t use a specific Markdown file for instructions, it is designed to automatically **understand project context and adhere to coding guidelines**. According to JetBrains, Junie “can adapt to your coding style” and “follow specific coding guidelines,” resulting in better alignment with the way your team writes code. How does it achieve this? Primarily through the IDE’s knowledge: it has access to the project’s code structure, existing code style settings (for example, JetBrains IDEs have configurable code style and inspection settings), and even static analysis tools. Junie uses IDE inspections and checks when making code changes, and it runs tests or code to verify outcomes. So instead of reading a file like Agents.md, Junie likely leverages the IDE’s configurations and any documentation already present (such as a README or inline comments). If your project has a `CONTRIBUTING.md` or coding standard document, a human would read that — Junie might not automatically read arbitrary Markdown files unless you prompt it, but because it “understands the context of any given project”, it may infer many guidelines from how the code is written and from the IDE’s settings. In practice, if Junie needs extra guidance (say, about architectural conventions not easily inferred), you could still feed it a description via the prompt (or a file content paste), but often it will try to “just know” by analyzing the project.
    

**Summary:** _Agents.md files (or their equivalents like Claude.md or copilot-instructions.md) provide persistent, context-wide instructions to AI coding agents._ They are most explicitly used in CLI-based agents like OpenAI Codex CLI and Claude Code. In more integrated tools (Copilot, Junie), the concept exists but is handled via repository instruction files or the IDE’s context rather than a literal Agents.md.

Next, we’ll explore **what information to put into** these files versus what to include in the direct prompt, for various types of guidance.

## Task Management and the “Coordinator” Role Instructions

One appealing feature of agentic coding systems is their ability to act as a **“project coordinator”** or “task manager,” breaking down a complex request into sub-tasks, deciding which files to edit, running tests, and iterating until the goal is achieved. All the mentioned platforms have this capability built-in to some degree: they are designed to plan and execute multi-step workflows autonomously. For example, GitHub Copilot’s agent mode will “plan and execute multi-step solutions… run commands or tests… and refine its work through an agentic loop” automatically. Similarly, OpenAI’s Codex agent was built to respond to errors and keep modifying code until tests pass, without the user explicitly directing each step.

**How much “process guidance” should you provide?** Generally, you do **not** need to write out detailed step-by-step task management instructions in Agents.md or in your prompt _when using these advanced agents_. The systems themselves provide a _system prompt_ or scaffold that instructs the AI to work in a loop (for Copilot, the backend prompt explicitly tells it to keep iterating until completion). Likewise, Codex CLI and Claude Code internally handle loops of read → edit → test → fix. This means you can usually just state **what** you want done (“Implement feature X” or “Refactor module Y for performance”) and the agent will determine **how** to break that down into steps.

- **Agents.md file:** It usually **does not need to include the step-by-step game plan** for task execution. You wouldn’t list “First open file A, then modify function B, then run tests, then…”. That kind of coordinator logic is the agent’s job. At most, in Agents.md you might include high-level **policy** guidance on process. For example, if you want the agent to always use a certain approach in its planning, you could state it generally. A realistic example: “When implementing new features, create or update unit tests accordingly” or “Prefer making small, incremental commits for each logically separate change.” These are guidelines that influence the _process_, but they aren’t specific steps – they’re principles the agent should follow while it manages the task. Agents.md is good for such principles or defaults (like “always run `npm test` after changes” – which overlaps with coding diligence, see next section). In contrast, writing out the entire project plan in Agents.md would be both impractical and unnecessary; the agent dynamically plans per prompt, and your static file should not micro-manage that.
    
- **Prompt (user query):** The prompt is where you specify the **current task requirements**. If the task is complex, you might break it down yourself across multiple prompts (iteratively), or rely on the agent to do it. In either case, you typically don’t have to tell the agent _how_ to plan (e.g. “first do X then Y”) unless you have a very particular process in mind that the agent wouldn’t guess. Most often, you let the agent’s internal coordinator role handle it. Only intervene in the prompt level if you notice the agent is approaching the task wrong or missing a step. For instance, if an agent forgets a sub-task, you can prompt: “Also ensure you update the configuration file as part of this change.” This becomes a direct instruction that overrides whatever the agent might have done by default. In fact, the Codex spec explicitly says **direct user instructions take precedence** over Agents.md or other context. So the prompt is your tool to adjust the plan on the fly, whereas Agents.md sets the baseline expectations.
    
- **Built-in agent logic:** All platforms will, on their own, attempt to handle the coordination. Copilot agent mode, for example, will autonomously decide relevant files and commands unless you explicitly add a file to focus it. JetBrains Junie uses IDE intelligence to find usages, run inspections, etc., as part of its autonomous workflow. Given this, you often **delegate task management to the agent**. Let it propose a plan; your role is to review its steps and results (which these tools surface in the UI) and intervene if it goes off track.
    

**Variation between platforms:** The more “open” the platform, the more you might need to specify. For example, if you were using a raw LLM (like the GPT-4 API) without an agent framework, then _you_ would have to prompt it to plan and iterate. But with Codex/Claude/Copilot/Junie, that scaffolding is there. Codex CLI even had different _autonomy modes_(“Suggest” vs “Auto Edit” vs “Full Auto”) to control how aggressively it proceeds on its own – you might choose a lower autonomy setting if you want to guide each step manually. Copilot agent mode similarly allows you to approve or undo certain actions (especially running terminal commands) as a safety check. Thus, for highly regulated environments, you might not permit full autonomy and instead step through each sub-task with the agent. In those cases, you’ll use the _prompt_ to approve or guide each step rather than pre-writing anything in Agents.md.

**Bottom line:** You usually **don’t put detailed multi-step task instructions in Agents.md**, because the agent platform already knows how to be a “coordinator.” Instead, use Agents.md to set general process rules (e.g. “always write tests for new code”), and use your prompts or the platform’s UI controls to handle specific task flow adjustments. Keep your prompts focused on _what outcome_ you want, not low-level how-to steps, unless the agent is misinterpreting the task. This leads to more natural collaboration where the human specifies the goal and the agent figures out the execution.

## Coding Standards, Testing, and Quality Assurance Instructions

One of the most valuable uses of an Agents.md-like file is to instill your **coding standards and quality practices** into the AI assistant. Without guidance, an LLM might produce code that doesn’t meet your style guidelines or might neglect to run tests. Here’s how to allocate these instructions:

- **Agents.md (persistent guidelines):** This is the ideal place to enumerate your project’s coding conventions, style requirements, and testing mandates. The OpenAI Codex documentation specifically notes that `AGENTS.md` can inform the agent about “coding conventions” and how to run or test the code. For example, you might include sections in Agents.md like: coding style (indentation, naming conventions, language-specific lint rules), architecture guidelines (“use repository layer for DB access instead of calling DB directly”), and test policy (“all new features must have unit tests; run `./gradlew test` to execute tests”). Because this file is always consulted by the agent (for any code it touches in that scope), it serves as a safety net to enforce diligence. The agent will try to follow these rules whenever relevant. In fact, if you provide test commands or checks in the Agents.md, the Codex agent is required to run them and verify they pass after making changes. So you _should_ list the exact commands to build and test the project (e.g. “To run the full test suite, use `npm run test`”) in the file. Similarly include any _cross-checking steps_ you expect (for instance, “After changes, ensure the README usage examples are updated if needed” or “Double-check that all public APIs have updated documentation/comments”).
    
    For Claude Code’s `Claude.md`, you would provide the same kind of information – style guides, important libraries or functions to use or avoid, testing instructions. According to a review, “specify things like: Test instructions, core files, code styling, guidelines, and other important information you want an agent to remember” in these files. By front-loading this in Agents.md/Claude.md, you free your prompt from having to repeat these every time and reduce the chance of the AI overlooking a standard practice.
    
    One caveat: make sure these instructions are **concise and clear**. Don’t overload the file with huge essay paragraphs. Use bullet points or short sections for each rule, because the model will have to absorb and apply them. Also, be aware of the context window – extremely long Agents.md files could be truncated or only partially attended to. Stick to the most impactful guidelines. For example, a handful of key “dos and don’ts” is better than pages of prose. (GitHub’s approach for Copilot’s instructions also recommends short, self-contained statements.)
    
- **Prompt (per-task instructions):** Even with a thorough Agents.md, there will be times you mention standards or tests in the prompt for emphasis. Use the prompt to **reinforce or override** as needed. For instance, if your Agents.md says “run all tests before finalizing”, you usually don’t need to repeat that in your prompt – the agent should do it. But if you notice it sometimes skips a slow integration test suite, you might explicitly prompt “make sure _all_ tests pass, including integration tests.” Prompts are also where you specify additional acceptance criteria for the particular task: e.g. “Implement feature X **and ensure it conforms to our performance guidelines (see Agents.md)**” – here you’re drawing its attention to a particular section of the guidelines relevant now. If you have an external style guide (say a separate `STYLEGUIDE.md` or an URL), you might cite or link it in the prompt if the change is heavily style-dependent. Another use of the prompt is when you are doing a one-off task that has special quality criteria not in Agents.md. For example, “We’re preparing a demo, so optimize for readability over performance for this snippet” – a rule that you wouldn’t make global, but is important for this request.
    
    In essence, rely on Agents.md for general standards, and use the prompt to call out anything context-specific or to correct the agent if it deviates from the standards. Keep in mind that if there’s a conflict, your prompt instruction wins. This means you shouldn’t hesitate to clarify in the prompt if the usual standard should be bent or followed in a particular way.
    
- **Platform delegation:** The agent platforms themselves also try to adhere to standard coding practices by default. For instance, Codex was trained to produce “cleaner patches” aligned with human preferences, and Junie “uses IDE inspections” to maintain code quality. Copilot can be configured with **organization-wide policies** in business settings (for example, an admin can set certain linting rules that Copilot will respect). There’s even a feature in GitHub Copilot for _code referencing and duplication avoidance_, etc., but these are behind-the-scenes. The bottom line: _Don’t assume the AI will know your project’s unique style without telling it._ It will do something reasonable (e.g. follow PEP8 in Python by default), but if your project differs (say, you use a specific naming convention or a particular test framework), you must inform it. The best place for that is your Agents.md or Copilot instructions file, as those persist. The per-repo Copilot instructions file is exactly intended to capture “codebase-wide context to each AI workflow” – for example, an entry in `.github/copilot-instructions.md` might read: _“Always use our internal utility functions for logging instead of print statements.”_ Once saved, that will be automatically attached to every prompt in Copilot Chat for that repo, so the AI is constantly reminded.
    
- **Testing and verification:** Agents.md should absolutely mention how to run tests or any required verification steps (linting, type-checking, etc.), because the CLI agents will then perform them. If your project has an unusual test command, or needs a local database seeded, etc., document that for the agent. These agents are quite diligent when instructed – for instance, Codex’s rules say if the Agents.md defines some “programmatic checks” (like a script or tests to run), the agent **MUST** run them and confirm they pass after its changes. In practice, you might add to Agents.md: “**Testing:** Run `pytest` in the `tests/` directory; all tests must pass. Also run `flake8` for linting; fix any warnings.” The agent will incorporate those into its workflow (Codex or Claude will execute them via their tool interface; Copilot will run tests in the integrated terminal and monitor output; Junie will do similarly via the IDE’s test runner).
    
    Still, you should remain vigilant. Verify that the agent indeed ran the tests – the UIs usually show this (e.g. Copilot agent mode displays terminal output as it runs commands). If something was missed, you might need to prompt it or run tests yourself and then feed back the results.
    

**How things can go wrong & how to correct:** Despite guidelines, agents can slip. For example, the agent might hallucinate a solution that “works” but doesn’t actually meet an implicit requirement. If you find the agent introduced a dependency against your instructions (say you said “don’t use external HTTP calls” but it did), you’d correct it by explicitly pointing that out in your feedback prompt: “The solution uses an HTTP call, but we disallow that. Please refactor to follow the project guidelines (no external HTTP; use our internal service interface).” This highlights a general strategy: **update your Agents.md over time** as you observe patterns of the agent’s mistakes. If you realize there’s a new rule to codify (“Stop using library X, we’ve moved to Y”), add it to Agents.md so the agent remembers next time.

The differences between platforms here largely boil down to _where_ to put the info:

- In Codex/Claude CLI, use their markdown files (Agents.md/Claude.md) for any and all style/testing rules.
    
- In GitHub Copilot, use the `.copilot-instructions.md` for broad rules (short and sweet, as recommended) and perhaps maintain a `STYLEGUIDE.md` or other docs in your repo that the agent can refer to. If it’s a Chat context, you can also simply tell Copilot “Follow our styleguide” and it might ask for it or try to open it if it’s in the repo. Copilot’s advantage is that it can _search your repository_: if you ask something and it’s documented in your repo, Copilot might find it. (It does a semantic index of the codebase in some configurations.) So storing detailed guidelines in a dedicated file (even if not `.copilot-instructions.md`) can help – you can then prompt “Open the STYLEGUIDE.md” or the agent might automatically fetch it if relevant.
    
- Junie, again, will inherently follow the coding standards configured in the IDE. For instance, if your IDE has code formatting rules, any code Junie writes and commits will be auto-formatted by the IDE’s standard. If you have inspections that forbid certain patterns, Junie is likely to catch and fix those as part of its process. So the effort of writing an Agents.md for style in Junie might be lower; still, any architectural or design guidelines that aren’t enforced by tooling should be communicated (either via an initial prompt to Junie when starting a task or via documentation that a developer using Junie can supply to it).
    

In summary, **use Agents.md or its equivalent to encode your team’s definition of “good code”** – style rules, naming conventions, approved/rejected practices, and the steps to verify code correctness. This allows the AI to act as a diligent developer that, for example, writes docstrings if you require them, uses the correct license headers, and runs the full test suite before considering a task done. Keep the prompt itself focused on the specifics of the feature/bug at hand, while trusting the persistent instructions to enforce global quality standards. And if you discover a gap, update the instructions file and/or clarify in your next prompt.

## Documentation Generation Tasks – How Much to Specify vs. Iterate

Using AI agents for generating documentation (e.g. user guides, API docs, code comments, README content) raises the question: should you instruct the agent exactly what documents to produce and their outline, or let it decide and refine it through feedback? The answer often depends on how clear your documentation needs are upfront and the capabilities of the agent:

- **Specifying documentation structure in Agents.md or prompt:** If your project follows a known documentation structure, you can certainly encode that. For example, some projects always have `README.md`, `CONTRIBUTING.md`, and maybe a `/docs/` folder with specific files (architecture overview, deployment guide, etc.). You can write in Agents.md: “Our documentation consists of: `/README.md` (high-level usage), `/docs/architecture.md` (design overview), `/docs/api.md` (API reference), etc.” However, whether the agent will autonomously create multiple files without being asked is uncertain. Most agents operate on the principle of fulfilling the user’s prompt. So if you simply say “Generate documentation for feature X,” by default it might produce one file or just a section of README unless told otherwise. Agents.md can hint at the format (for instance: “Documentation for new features should include updates to the README and a section in the CHANGELOG”), but it won’t automatically spawn new files unless the task prompt implies that.
    
    A safer approach is to **decide on the documentation scope and specify it in your prompt** when kicking off the task. For instance: _“Write documentation for the Foo module. This should include: (1) Updating the main README if needed, (2) Creating a `Foo.md` in the docs folder describing the module’s design and usage, and (3) adding docstrings to all public methods in the Foo module.”_ This explicit instruction in the prompt tells the agent exactly what deliverables you expect. It leaves less to chance. If you omit such detail, an agent like Copilot or Claude might just produce a README update or a single file it deems most relevant, potentially missing pieces.
    
    That said, there is a trade-off: if you over-specify without knowing what’s needed, you might waste time. Perhaps not all those documents are necessary. If you’re unsure of the ideal structure, you can instead _ask the agent for a proposal_. For example: “I need to document the new Foo feature. What documents or sections do you suggest creating?” The agent might then outline a few items, which you can approve or tweak before it writes them. This iterative approach leverages the AI’s ability to organize content.
    
- **Iterative drafting and refinement:** Documentation is often best done iteratively. A recommended strategy is:
    
    1. **Outline Phase:** Ask the agent to produce an outline or list of topics for the documentation. Review this yourself. This ensures the AI’s understanding of what needs documenting aligns with yours. If it missed something or included too much, you can correct the course early. For example, “Outline the sections for the Foo module documentation.” You get a skeleton like: “Introduction, Installation, Usage Example, API details, FAQs.” You might realize an FAQ isn’t needed but a “Troubleshooting” section is – you can adjust and instruct the agent accordingly.
        
    2. **Draft Phase:** Have the agent fill in one part at a time. You can say, “Great, now write the Usage Example section.” Working section by section (or file by file if multiple files) helps manage complexity and allows you to review incrementally. It’s similar to how you might not ask it to generate 1000 lines of code in one go, but rather one function at a time for better control.
        
    3. **Review and Revise:** Read the drafts carefully. LLMs can produce plausible but incorrect information, especially in documentation where details matter. Check that any technical descriptions the agent wrote are accurate. If the agent assumed or made up anything uncertain (for example, it might hallucinate a config flag or misstate how a function works), flag those. You then feed corrections: “The description of the FooBar function is wrong about its parameters – please fix that according to the code.” Because the agent has access to the code, it can cross-check (some agents can even be prompted to open the source file to ensure docs match code). Claude and GPT-4 are particularly good at consistency if prompted to double-check. Copilot might not automatically cross-check every detail unless asked, so explicitly telling it to verify against the code can help. This review loop may go a couple of rounds.
        
    4. **Polish:** Once content is correct, you might ask the agent to format or improve clarity (“Add bullet points for the steps”, “Make sure the tone is friendly and clear for beginners” etc.). Since writing style is subjective, you guide the AI to match your desired tone.
        
- **Where to put instructions for documentation tasks:** Agents.md can contain general documentation guidelines. For example: “All modules must have API documentation in the `docs/` folder. Tutorials should go in `docs/tutorials/`. Use Markdown headings and include code examples.” This gives the AI a frame of reference. The agent, upon reading that, might know to check for a docs folder or at least to mention documentation updates in its plan. But _creating new docs is usually triggered by the prompt._ So your prompt should clearly state that documentation is the goal. If you have specific output files in mind, list them. If you don’t, you can prompt the agent to help determine what’s needed, as described.
    
    In Copilot’s case, if you have a `docs/` directory, the agent mode might deduce that documentation should go there (especially if similar files exist as examples). In Junie’s case, since it works with the IDE, it might not spontaneously create new files without being directed, so you likely have to instruct it (“create a new Markdown file for X”). Junie will, however, happily write doc comments and such if asked, and can integrate with the IDE’s Markdown editor.
    
- **Human review is key:** No matter how detailed your initial instructions, when it comes to docs, plan for a human-in-the-loop. The AI can produce a lot of text confidently, but you are responsible for its accuracy and usefulness. The user prompt can be used after each iteration to refine: e.g., “Expand the explanation of how Foo handles errors,” or “Simplify the language in the introduction for a novice audience.” These kind of refinements are normal – treat the AI as a junior technical writer: it can generate a draft quickly, but you must edit and guide it to the final polished state.
    
- **Specify or iterate?** **It’s often wise to iterate based on first results and human review rather than specify everything 100% upfront**. Why? Because you might not know exactly what to specify until you see a draft. For instance, you might think you want a separate FAQ, but after seeing the main doc, you realize it’s unnecessary. If you had instructed the agent initially to create an FAQ file, you’d have to roll that back. It’s more efficient to let the agent produce a reasonable first pass, then course-correct. In fact, the VS Code team noted that instead of relying on one long, detailed prompt to get a perfect output, _“you should iterate with Copilot – the UI is built for iterations, giving you full control to ensure the final result is better”_. This principle holds for documentation as well: start simple, then refine in cycles.
    
- **One exception**: if you have **non-negotiable doc requirements**, state them early. For example, if it’s critical that the documentation includes a particular disclaimer or follows a certain template, do mention that upfront (in prompt or Agents.md). You don’t want the AI to omit it and then have to insert it later manually. Critical structural or content mandates should be given to the AI so it won’t forget them.
    

**In summary**, for documentation tasks use a combination of upfront guidance and iterative refinement:

- Use Agents.md to inform the agent of general documentation practices (locations, format, style).
    
- Use the prompt to clearly state the documentation deliverables you expect for the current task (especially number of files or sections).
    
- If unsure of details, leverage the agent’s suggestions (ask for an outline) then iterate.
    
- Always review and correct the AI’s documentation output; consider it a draft to be improved through dialogue. This approach ensures the docs are accurate and well-structured without you having to predetermine everything sight unseen.
    

## Iteration and Refinement Strategies in an AI-Assisted Project

Integrating AI coding agents into your workflow is an ongoing, iterative process itself. As you get deeper into a project, here are strategies to manage the agent’s performance and steer it effectively:

- **Start Small, Then Scale Up:** At the beginning of a project (or the start of using an AI agent on an existing project), give it smaller, well-defined tasks. Evaluate its output and learn its quirks. For example, first ask it to add a simple unit test or refactor a small function. Review how it does it – did it follow your style? Did it run tests? This helps validate that your Agents.md or instruction file is being respected. Once confidence builds, you can assign larger tasks. If you jump into a huge feature implementation on day one, you might miss the chance to fine-tune your guidance on simpler tasks. Treat it like onboarding a new team member: gradually increase responsibility.
    
- **Continuous Agents.md Refinement:** Keep your project’s AI guidelines up to date. After each significant agent interaction, reflect: _Did the AI make an avoidable mistake or ask for something it should know?_ If yes, that’s a cue to update the instructions. For instance, if it generated a function with no docstring but you want docstrings always, add “All functions must have a docstring” to Agents.md. If it repeatedly uses a deprecated API, add “Do not use API X; use Y instead.” This way, the more you use the agent, the smarter it operates within your context. (Remember that changes to Agents.md or copilot-instructions.md take effect immediately for future prompts.)
    
- **Use Version Control and Branches:** Most agentic tools either directly integrate with version control or encourage small commits. It’s wise to let the agent work in a separate branch (or at least review its diff before merging to main). GitHub Copilot agent can create pull requests for its work, which you can review. Codex CLI likewise can commit to a new branch and push. By isolating changes, you can run your full CI pipeline on them and do code review as usual. If something is wrong, you can roll back or ask the agent to fix the specific issues. This safety net is crucial for larger code edits.
    
- **Monitor Agent’s Actions:** In Copilot’s agent UI, every action (file edit, command run) is visible to you in real time. Similarly, Junie will show what it’s doing in the IDE (e.g., you’ll see files open, text being inserted, tests running). Pay attention to this. If the agent starts doing something you didn’t intend (like modifying an unrelated file, or installing an unexpected package), intervene. With Copilot, you can hit “Undo Last Edit” to revert an undesired change. With CLI agents, you might have an approval mode off to catch such cases. It’s easier to correct a wrong turn early than after it has compounded. For example, if the agent’s first approach to a problem is clearly off-track, stop it and clarify via prompt before it edits more files under that false assumption.
    
- **Detecting Wrong Turns:** Signs of the agent going astray include: tests failing repeatedly without progress, the agent fixating on a solution that you know is suboptimal, or the agent asking for irrelevant information. If your agent is in a loop of trying similar fixes and not succeeding, it might need new direction. For example, maybe the real issue is different from what it thinks. In such cases, break the loop by giving a hint or changing strategy in the prompt. You could say, “It looks like the approach isn’t working because of X, maybe try a different strategy involving Y.” The agent will incorporate your hint into its next plan. Essentially, you act as a coach to the AI when it stalls out.
    
- **Leverage Multiple Models if Available:** If you have access to both GPT-4 based and Claude models (for instance, Copilot might allow choosing between GPT-4 or Anthropic in the future), you could try the same prompt on another model if one gets stuck. Sometimes one model’s insight can unjam a problem the other struggled with. This is more of an advanced technique and may not be necessary often, but it’s good to know if you have the tools at your disposal (the user did mention having Claude and Codex access separately). In practice, you might use the CLI tools interchangeably – e.g., ask Claude Code for a second opinion on a complex refactor if Codex’s solution seems incomplete.
    
- **Templates and Reusable Prompts:** As you iterate, you’ll discover prompt phrasings that work well. It’s useful to save these as templates. For example, a prompt template for writing tests might be: “**Task:** Write unit tests for the XYZ module. **Requirements:** Use our standard testing library, cover all public functions, aim for >90% coverage. If any bugs are found in the process, fix them. **Context:** (list of files or brief summary).” You can reuse such structured prompts for similar tasks in the future. Some tools let you save prompt snippets or have a “prompt library” (Copilot has a Prompt Library in the Chat UI, and others like Cursor support saved prompts). This ensures consistency and saves time. Likewise, you might maintain a **checklist** for code reviews that the agent does: e.g. “Did it update docs? Did it handle edge cases? Did it run tests?” – you can use this checklist to systematically review agent PRs or outputs, which feeds back into how you prompt it next.
    
- **Human Oversight and Limits:** Always remember that these agents, as advanced as they are, can make mistakes a human wouldn’t. They lack true understanding and may occasionally produce insecure code, logic errors, or just weird solutions. They also don’t know your product or end-users like you do. So keep a human critical eye on everything. Use the AI to accelerate mundane work (scaffolding, boilerplate, initial drafts), but let human insight drive the creative and critical decisions. If an agent suggests an architectural change, analyze it as you would a colleague’s suggestion – don’t just accept it because “the AI said so.” Often, the best results come from a tight collaboration: you iteratively refine what the AI produces, and the AI iteratively incorporates your feedback. Each iteration should get you closer to what you want, and importantly, help _you_ refine your understanding of the problem as well.
    
- **Know When to Stop or Split:** Sometimes an agent might reach the limits of what it can handle in one go – perhaps the task turned out to be more complex than anticipated. If you sense the conversation is getting convoluted (e.g., the context window is nearly maxed out with a lot of history, or the AI is starting to forget earlier instructions), it might be time to stop and summarize. You can end the current session and start a fresh one with a clean prompt that includes the latest state (maybe summarizing what’s been done and what remains). This avoids the model getting confused by a long interaction history. Another tactic is to break the task: “Alright, let’s put aside sub-problem A for now and focus on sub-problem B.” Solve B, then circle back to A. The Agents.md file here can serve as a persistent memory of overall goals so that even if you restart a session, the AI still knows the overarching guidelines and can pick up where it left off, context-wise.
    
- **Keep the Conversation Open:** Especially with Copilot and Junie, you have interactive chat. Don’t treat the agent as a fire-and-forget code generator. Ask it questions if something in its plan is unclear: “Why did you choose to do X?” The agent’s answer might reveal a misunderstanding. Copilot’s agent will show reasoning to some extent (like which tools it’s picking), and future UIs might expose the chain-of-thought more. Even now, you can prompt something like “Explain how the solution works” after it proposes code – a form of self-review. This can often highlight if it misunderstood the requirement. If the explanation doesn’t align with what you wanted, you know a correction is needed.
    

Finally, it’s worth noting that each of these platforms is rapidly evolving. New features (like improved context handling, better integration of custom rules, or more autonomy controls) are likely to appear. **Stay updated** on release notes – for example, GitHub’s documentation shows new capabilities like MCP (Model Context Protocol) which lets you plug in external tools or data sources if needed. These can further enhance how the agent works (for instance, connecting to your company’s internal knowledge base to answer questions). As these tools grow, some things you once had to prompt explicitly might become automatic. Continuously adjust your strategy with the agent as it improves.

## Conclusion

**Agents.md and similar instruction files are powerful tools for aligning AI agents with your project’s needs**, but they are not a panacea – they work best in concert with thoughtful prompting and active human supervision. In summary:

- **OpenAI Codex and Claude Code:** Use their markdown instruction files to the fullest. Include details on project structure, coding style, testing commands, and any specific dos/don’ts. These agents will read and obey those instructions diligently. Keep the file scoped and updated, and remember you can have hierarchical Agents.md files for different parts of a codebase if needed (with more specific rules overriding general ones).
    
- **GitHub Copilot (Agent Mode):** Enable and use the repository custom instructions file (`.github/copilot-instructions.md`) to give Copilot context about your codebase’s conventions. It’s a direct parallel to Agents.md functionality. Additionally, leverage the ability to feed it specific files or references in the prompt for more detailed context when necessary. Since Copilot’s agent is quite autonomous, focus on clearly stating the end goal in your prompt and let it handle the steps, but don’t hesitate to add guidance in prompts for any special cases. Keep instructions short and pertinent, as per GitHub’s recommendations.
    
- **JetBrains Junie:** Rely on its deep IDE integration. Ensure your IDE’s code style settings and inspections are configured to your liking – Junie will naturally follow those. Provide it with high-level goals and perhaps point it to any design docs or tickets describing the task. It will do a lot implicitly (run tests, maintain quality) thanks to the IDE’s capabilities. You won’t have an Agents.md, but you might maintain a project README or developer guide that a human collaborator (or Junie via prompt) can refer to for understanding the big picture. Junie aims to be a “trusted teammate” by understanding context, so the more standard your project’s structure and guidelines, the more it will pick up without extra instruction.
    
- **Task vs. Guidelines Split:** Put enduring knowledge (style guides, project policies, recurring commands) in the persistent instruction file (Agents.md / Claude.md / Copilot instructions). Put transient, task-specific instructions in the prompt. This separation ensures the agent is neither clueless about your standards nor overwhelmed with unnecessary detail for each query.
    
- **Iteration over Perfection:** Embrace an iterative workflow. As the Copilot team suggests, you’ll get better results by iterative prompting and refinement rather than trying to craft the “perfect” one-shot prompt. Use the agent’s feedback and output as a guide for what to ask next. This applies to coding tasks, debugging, documentation, and more. Each platform provides mechanisms (undo, edit, chat history) to support an interactive approach rather than one-and-done queries.
    
- **Error Correction and Safety Nets:** Always validate the agent’s output – run the tests yourself, do code reviews, and keep an eye on security and correctness. The agent will attempt these, but ultimate responsibility lies with the developer. Tools like Agents.md help minimize errors by informing the AI, but they don’t eliminate the need for human judgment. Keep your version control handy and don’t be afraid to backtrack if needed.
    

By thoughtfully distributing information between **Agents.md files (persistent context)** and **prompts (immediate instructions)**, and by leveraging each platform’s strengths, you can significantly enhance the AI’s understanding of your intent. The result is an AI pair programmer that not only writes code, but writes the _right_ code in the _right_ way – aligned with your project’s standards and objectives. And with vigilant iteration and guidance, you’ll effectively collaborate with these agentic tools to boost productivity while maintaining quality and control.
